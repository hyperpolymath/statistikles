=== [Unreleased]

==== Fixed

* `.github/workflows/release.yml` no longer declares `contents:` twice in the
  `provenance` job's `permissions:` map. The duplicate was appended by the #98
  permissions sweep on top of an existing `contents: write`, and a duplicate key
  is not an override — it is a parse error. GitHub answered `Invalid workflow
  file: (Line: 199, Col: 7): 'contents' is already defined`, which is a `failure`
  run with zero jobs, no log and no check run, so the release pipeline was
  silently dead from 2026-09-21 until now. `contents: write` is the line kept:
  the SLSA generator this job calls uploads the release assets.
* `.github/workflows/actions.lock` records `github/codeql-action@v4.38.1`, which
  `codeql.yml` has pinned since the Dependabot bump in #102 while the lock still
  said `v4.38.0`. An unvalidatable lockfile is not a warning: GitHub answers
  `Invalid lockfile: .github/workflows/actions.lock#L1 — The lockfile could not
  be validated. Regenerate it by running `gh actions-lock`` and refuses to start
  the run. That is why "CodeQL Security Analysis" had been a `startup_failure`
  with zero jobs on every push since 2026-09-25T08:33Z. The same rule is why the
  probe below could not start: refs with no lockfile entry are refused too.
* `.github/workflows/secret-scanner.yml` re-pinned to the
  `secret-scanner-reusable.yml` revision the estate's own template carries
  (`210f14e7…`, from `rhodium-standard-repositories`), and a new minimal
  `.gitleaks.toml` extends the estate baseline it stages. The old pin predated
  the shared allowlist (`config/gitleaks/estate-baseline.toml`), so this Julia
  repo's public package UUIDs (`Project.toml`) and `git-tree-sha1` integrity
  hashes (`Manifest.toml`) — exactly the false-positive class the baseline
  documents — were reported as candidate secrets on every run, and the pin's
  scan had no `--verbose`, so the log named neither the rule nor the file. The
  scanner has been red on every push for as long as the visible history goes.
  The new revision inherits the baseline, names its findings, and adds a gating
  full-history pass; if the job is still red after this, its log now says
  exactly which rule, file and line, which is what it could not do before.
* `.githooks/validate-workflow-permissions.sh`: the `expand()` docstring now says
  what the function does — a file path is returned as a one-item list, a
  directory expands to the sorted `.yml`/`.yaml` entries directly inside it, and
  no matches yield an empty list. Documentation only; no behaviour change. This
  is the clarification PR #110 was opened to land and did not: its merge commit
  had a single parent, so it changed nothing on `main`.

==== Changed

* `.githooks/validate-workflow-yaml.sh` (Dogfood Gate job "Workflows parse (no
  silent-dead gates)") now reads for the three ways a workflow file "parses" and
  is still refused by GitHub: duplicate keys (measured here: `release.yml`, see
  above), a missing `on:` trigger (measured here: the m3 probe), and
  `timeout-minutes` on a reusable-workflow call job (from the estate's canonical
  parser, standards@092deda). All three are 0-job failures with no check run, so
  a parse-only check cannot see them; the new checks fire on planted fixtures and
  agree with the estate's `check-workflow-duplicate-keys.sh`.

==== Removed

* `.github/workflows/zz-m3-no-on.yml`, the m3 leg of the #104 diagnostic matrix.
  Its question is answered: a workflow with no `on:` key is refused by GitHub
  with `No event triggers defined in `on``, which is a red 0-job run named by
  file path on every push, with no check run and no log. The matrix has run and a
  probe that can only ever fail is permanent noise on the board — the answer is
  recorded here instead (git history keeps the file).
* `.github/workflows/zz-pages-perms-probe.yml`, self-described as "TEMPORARY
  probe — delete before merge". It never started once: ten runs, ten
  `startup_failure`, every one refused with an allowlist message ("The actions
  actions/checkout@v7.0.1 and actions/upload-pages-artifact@v5.0.0 are not
  allowed in hyperpolymath/statistikles because all actions must be from a
  repository owned by hyperpolymath, created by GitHub, verified in the GitHub
  Marketplace, or match one of the patterns ..." — run 36177415819). The only
  measurable difference from the real `pages.yml`, which uses those same two
  refs and starts fine, is that the probe has no `actions.lock` section; both
  readings of that message end at the same conclusion, that the probe cannot
  be made to run from here. Both claims
  it was written to measure are now demonstrated by the real workflow on `main`:
  run 36177413215 built the site with `contents: read` only and deployed with
  exactly `pages: write` + `id-token: write`, at job level.
* `.github/workflows/zz-m1-plain-push.yml` and
  `.github/workflows/zz-m5-wrapper-shape.yml`, the remaining two legs of the
  #104 diagnostic matrix, retired in the same commit as their answers. The
  question they were built for is closed: GitHub refuses every run triggered by
  `arena-ai-coding-agent[bot]` with `Actor is not allowed to trigger Actions
  workflows` (12 of the 12 it triggered in this repo), while the maintainer's
  and CodeRabbit's runs start normally — so an agent-authored branch can never
  show CI, and the failure mode blamed on the matrix was really the lockfile
  and allowlist refusals above. Neither probe measured anything the real
  workflows do not already cover: `m1` was `on: push` plus one `echo`, and
  `m5` called the same standards `hypatia-scan-reusable.yml` that the shipped
  `hypatia-scan.yml` calls. The shapes are one `gh workflow run` away in git
  history if a canary is ever needed again.
* `.github/workflows/instant-sync.yml` and its `actions.lock` entry. Its only
  effect was a cross-repo `repository_dispatch` to
  `hyperpolymath/.git-private-farm`, which was retired with the Nix mirrors
  (standards#106) and no longer resolves; the secret-presence gate cannot detect
  a *revoked* token, so every push to `main` was red (#32). Estate CI/CD
  regularisation lists `instant-sync` under "never re-add".

==== Added

* `.gitleaks.toml` at the repo root: `[extend] path = ".gitleaks-estate.toml"`,
  which is the documented way a repository opts into the estate
  gitleaks baseline. The reusable stages that file only when a repo-local
  config references it by exactly that path, and stages the copy pinned to the
  reusable's own revision, so the config and the scanner consuming it are the
  same commit. No repo-local suppressions: the baseline covers the
  false-positive classes, and anything it does not cover is real until shown
  otherwise.
* `.githooks/validate-actions-lock.sh`, run in the "Workflows parse (no
  silent-dead gates)" Dogfood Gate job: fails when a workflow and
  `actions.lock` disagree, when the lock keeps a section for a deleted
  workflow, or when a locked ref has no valid `dependencies:` entry. It is
  bash-only and offline — `gh actions-lock` cannot be installed in the
  environment that wrote it (release-asset download EOFs), and a gate that
  needs a working third-party download to notice a stale lock is not a
  backstop. Verified against seven fixtures, including the real pre-fix lock
  from `0b45d60`, which it flags as `github/codeql-action@v4.38.0` in the lock
  vs `@v4.38.1` in `codeql.yml` (the `startup_failure` above).
* `.githooks/validate-workflow-permissions.sh`, run as a Dogfood Gate job: fails
  when `pages: write` / `id-token: write` are granted workflow-wide, or when any
  `permissions:` block is `write-all`. This is the regression guard for #66 —
  the over-grant was invisible for months because nothing read the grant.
